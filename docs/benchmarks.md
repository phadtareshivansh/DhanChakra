# Dhan-Chakra — Fraud Risk Scorer Benchmark

Reproducible comparison of four scorers on the synthetic AML-style graph (`api/app/services/gnn/synthetic.py`). Generated by `api/benchmarks/run_benchmark.py`.

> **Data is synthetic.** Graphs are generated by `synthetic.generate_graph`: clean companies plus planted invoice rings. A label of **1 means the company was placed in a planted ring**; 0 means clean. These numbers measure **the pipeline**, not real GST fraud detection rates.

## Protocol

- **60 graphs** per seed x **5 seeds** (1, 2, 3, 4, 5).
- **Graphs** (not nodes) split 60/20/20, stratified by positive count, seeded — *identical for every model within a seed*.
- Splitting by graph is required: GraphSAGE aggregates along edges, so a node split would leak test labels into training.
- F1 decision threshold is chosen on the **validation** split only, never on test.
- precision@k / recall@k are **pooled** over the test-node ranking (top-k alerts triaged), k = 50, 100.
- Reported as **mean ± std** across seeds.

Test-node pool per seed: **192 nodes**, **64 positives** (prevalence ~0.333).
k values — k=50: used 50; k=100: used 100.

## Headline results

**precision@k / recall@k are the headline metrics here**, not AUC-PR. At this graph size AUC-PR saturates (see *Why AUC saturates* below), so it cannot rank the models; P@k/R@k measure what actually matters — how many of the top-k alerts an investigator triages are true ring members. Rows are ordered by R@50.

Features are recomputed from **edges only** (`build_features(edges, n)`), with no cycle feature and no access to the generator's matrix.

## Does GraphSAGE beat gradient boosting?

**Essentially tied** (within noise). On the headline table (recall@50) GraphSAGE scores 0.735 ± 0.048 vs GBM 0.744 ± 0.041 (delta -0.009); P@50 delta -0.012; AUC-PR delta -0.002.

This is an honest outcome to report. On these small synthetic graphs with planted rings, per-node structural features are already strong and gradient boosting exploits them as well as GraphSAGE's neighbourhood aggregation. GraphSAGE's advantage would be expected on larger, noisier graphs where a node's own features are not enough.

## Why AUC saturates (and why P@k is the headline)

On the headline view AUC-PR reaches ~1.000 for the learned models. That is **not leakage** — the label-shuffle check below shows every view collapsing to chance — it is the toy generator being too easy at 24 nodes:

- Ring members are wired as a **closed loop with deliberate mutual edges** (`noise_edges=0.3` adds the reverse edge). Clean companies almost never form mutual edges, so `reciprocity` alone carries **AUC-ROC ~0.78**.
- `clustering`, `pagerank` and `shared_neighbors` add further weak but real signal, and together they let LR/GBM separate the classes nearly perfectly.
- Concrete check: pure cycle detection on the edges finds ring members at **recall 1.00, precision ~0.56–0.73** per graph — the loop is topologically obvious.

Because ranking metrics saturate, **precision@k / recall@k are reported as the headline**: at k=50 they do not saturate (P@50 ~0.68 for the best model) and they answer the operational question — *of the top-k alerts an officer triages, how many are real?*

## Leakage

**What leaked.** `synthetic.generate_graph` computes its feature columns from the same `in_ring` flag it uses to set the label:

| Generator column | How it depends on `in_ring` |
|---|---|
| `cycle_member` | `1.0 if in_ring else 0.0` — **exact label copy** |
| `pagerank` | `uniform(0.05,0.15) + (0.3 if in_ring else 0)` |
| `betweenness` | `uniform(0,0.05) + (0.2 if in_ring else 0)` |
| `shared_director` | disjoint ranges by `in_ring` |
| `shared_address` | disjoint ranges by `in_ring` |
| `community_share` | ring members share community 0 |

**So 7 of 8 generator columns are label-derived** and the generator's feature matrix cannot be used for honest evaluation.

**How it was excluded.** The headline view is recomputed from edges alone by `build_features(edges, n)`, whose signature cannot receive labels, ring membership, or the generator's matrix. `cycle_member` is excluded from the headline and appears only in the flagged `B + recomputed cycle feature` row, recomputed by real cycle detection.

**Rule baseline.** Allowed to use cycle membership, because that *is* the rule — but it computes it itself from the edges rather than reading the generator's label-copy column, so it is a fair stand-in for the structural layer.

**Missing features.** The generator stores no director or address data, so shared-director / shared-address could **not** be recomputed and were dropped rather than fabricated; `shared_neighbors` (edge-derived) stands in as a structural signal.

**Label-shuffle sanity check.** After permuting labels within each graph, learned models should collapse to chance. Observed:

| View | Model | AUC-PR | AUC-ROC | Prevalence |
|---|---|---|---|---|
| `edge` | `logistic_regression` | 0.406 | 0.570 | 0.354 |
| `edge` | `gradient_boosting` | 0.435 | 0.626 | 0.354 |
| `floor` | `logistic_regression` | 0.430 | 0.538 | 0.354 |
| `floor` | `gradient_boosting` | 0.406 | 0.499 | 0.354 |
| `leak` | `logistic_regression` | 0.419 | 0.514 | 0.354 |
| `leak` | `gradient_boosting` | 0.462 | 0.623 | 0.354 |

**Recommended follow-up (not done here).** `synthetic.py` should be changed to generate features independently of `in_ring` (e.g. draw structural properties from the graph topology after the labels are fixed), so its feature matrix becomes usable for evaluation. This task deliberately did **not** modify `synthetic.py`.

## Caveats

- Results are on **synthetic graphs with planted rings** and may overstate real-world performance. They measure the pipeline end to end, not real GST fraud detection rates.
- Five seeds is enough to show variance, not enough for tight confidence intervals.
- `precision@k`/`recall@k` pool across test nodes from multiple graphs; k is clamped to the pool size when the pool is smaller than k.

## Reproduce

Every number in this document was measured, not estimated. To reproduce:

```bash
make up                # build + start the stack
make benchmark         # runs the harness in the api container, copies artifacts back
```

`make benchmark` executes, inside the `api` container:

```bash
python /benchmarks/run_benchmark.py --out-dir /tmp/benchmark_out
```

and then copies `results.json`, `pr_curve.png` and `benchmarks.md` back to
`api/benchmarks/` and `docs/benchmarks.md`.
