## Protocol

- **60 graphs** per seed x **5 seeds** (1, 2, 3, 4, 5).
- **Graphs** (not nodes) split 60/20/20, stratified by positive count, seeded — *identical for every model within a seed*.
- Splitting by graph is required: GraphSAGE aggregates along edges, so a node split would leak test labels into training.
- F1 decision threshold is chosen on the **validation** split only, never on test.
- precision@k / recall@k are **pooled** over the test-node ranking (top-k alerts triaged), k = 50, 100.
- Reported as **mean ± std** across seeds.

Test-node pool per seed: **192 nodes**, **64 positives** (prevalence ~0.333).
k values — k=50: used 50; k=100: used 100.

## Does GraphSAGE beat gradient boosting?

On the headline table (recall@50) GraphSAGE scores 0.735 ± 0.048 vs GBM 0.744 ± 0.041 (delta -0.009); P@50 delta -0.012; AUC-PR delta -0.002.

**Essentially tied** (within noise). On the headline metric this is the honest reading of the numbers above.

This is an honest outcome to report. On these graphs, per-node structural features are already strong and gradient boosting exploits them as well as GraphSAGE's neighbourhood aggregation. GraphSAGE's advantage would be expected on larger, noisier graphs where a node's own features are not enough.

## Why AUC saturates (and why P@k is the headline)

On the headline view AUC-PR reaches ~1.000 for the learned models. That is **not leakage** — the label-shuffle check below shows every view collapsing to chance — it is the toy generator being too easy at 24 nodes:

- Ring members are wired as a **closed loop with deliberate mutual edges** (`noise_edges=0.3` adds the reverse edge). Clean companies almost never form mutual edges, so `reciprocity` alone carries **AUC-ROC ~0.78**.
- `clustering`, `pagerank` and `shared_neighbors` add further weak but real signal, and together they let LR/GBM separate the classes nearly perfectly.
- Concrete check: pure cycle detection on the edges finds ring members at **recall 1.00, precision ~0.56–0.73** per graph — the loop is topologically obvious.

Because ranking metrics saturate, **precision@k / recall@k are reported as the headline**: at k=50 they do not saturate and they answer the operational question — *of the top-k alerts an officer triages, how many are real?*

## Leakage

**What leaked.** `synthetic.generate_graph` computes its feature columns from the same `in_ring` flag it uses to set the label:

| Generator column | How it depends on `in_ring` |
|---|---|
| `cycle_member` | `1.0 if in_ring else 0.0` — **exact label copy** |
| `pagerank` | `uniform(0.05,0.15) + (0.3 if in_ring else 0)` |
| `betweenness` | `uniform(0,0.05) + (0.2 if in_ring else 0)` |
| `shared_director` | disjoint ranges by `in_ring` |
| `shared_address` | disjoint ranges by `in_ring` |
| `community_share` | ring members share community 0 |
| `eway_mismatch` | correlated but noisy — ring members draw `uniform(0.5,1.0)`, except 25% of them which draw `0.0` |
| `burst_indicator` | correlated but noisy — `1.0` with probability 0.6 for ring members, 0.08 otherwise |

**So all 10 generator columns are label-derived** (the first 8 directly, the last 2 stochastically) and the generator's feature matrix cannot be used for honest evaluation.

**How it was excluded.** The headline view is recomputed from edges alone by `build_features(edges, n)`, whose signature cannot receive labels, ring membership, or the generator's matrix. `cycle_member` is excluded from the headline and appears only in the flagged `B + recomputed cycle feature` row, recomputed by real cycle detection.

**Rule baseline.** Allowed to use cycle membership, because that *is* the rule — but it computes it itself from the edges rather than reading the generator's label-copy column, so it is a fair stand-in for the structural layer.

**Missing features.** The generator stores no director or address data, so shared-director / shared-address could **not** be recomputed and were dropped rather than fabricated; `shared_neighbors` (edge-derived) stands in as a structural signal.

### False-positive stress test (legitimate supplier cluster)

A deliberately benign, tight-knit cluster (30 nodes, dense internal trade, no
closed cycles, **no** shared directors/addresses) is scored with models trained
on the real data. Thresholds are chosen on the **real data's validation split**,
never on the cluster. Every cluster node is a true negative, so **any flag is a
false positive**.

| Model | chain: mean flag rate | chain: max | star: mean flag rate | star: max |
|---|---|---|---|---|
| `logistic_regression` | 0.260 | 0.933 | 0.467 | 0.800 |
| `gradient_boosting` | 0.153 | 0.400 | 0.040 | 0.067 |
| `graphsage` | 0.120 | 0.133 | 0.520 | 0.800 |
| `rule_only` | 0.400 | 0.467 | 0.180 | 0.300 |

**This is a real finding, not a passing grade.** GraphSAGE is the *best* model on
the chain cluster (0.12 mean flag rate) and the *worst* on the star cluster
(0.52 mean, up to 0.80). A benign hub — one buyer purchasing from many
suppliers — looks like a laundering hub to neighbourhood aggregation. GBM is
robust on the star (0.04). The rule-only baseline flags the chain heavily (0.40),
because a long directed supply chain is structurally close to what the rule
targets. Operators should read this as: **top-k ranking quality and
false-positive behaviour are different questions, and the best-ranking model is
not automatically the safest to deploy.**

**Loader behaviour (why it is defensive).** We could not verify the published
header from here, so `api/benchmarks/amlworld_loader.py`:

- validates the header on load and **fails fast** with both the header it found
  and the header it expected — it never silently misparses;
- matches column names **case-insensitively and ignoring surrounding
  whitespace**;
- handles the **duplicate `Account` header** positionally (column for the
  sender, next for the receiver), so it works whether or not the duplicate is
  present;
- reads in bounded chunks (streaming) rather than loading the whole table.

On load it prints a **short load report** — rows read, rows skipped and why,
accounts created, laundering-labelled transactions, derived positive accounts —
so you can sanity-check it against the dataset page.

### Identity: `(bank, account)`, not the account string alone

Account identity is the pair **`(bank, account)`**, not the account string on its
own, because the same account string can legitimately appear under different
banks in this data. Edges are keyed by that pair and reported as `BANK:ACCOUNT`.
The same rule applies to both endpoints. This is a deliberate modelling choice,
stated here so it is not mistaken for something the dataset provides.

### Labels: the real dataset labels *transactions*, we derive *accounts*

The real dataset's native label is per **transaction** (`Is Laundering`). Our
node-level label is **DERIVED**: an account is positive if it *participates in at
least one laundering transaction*. That derivation is ours, not the dataset's.

> **Known weakness.** A legitimate account that merely *receives* laundered funds
> — a downstream supplier paid by a launderer, say — is labelled positive. This
> penalises the model for not flagging a genuine, unwitting recipient and
> inflates apparent error. It is a label-definition artifact, not a model
> failure. To keep this honest, the generated block also reports an **edge-level
> metric on the native `Is Laundering` label**.

## Caveats

  synthetic datasets are self-written and use planted structures; they may
  **overstate** real-world performance. They are not evidence about IBM AMLworld,
  and IBM AMLworld results are not evidence about the synthetic ones.
- **The real table rests on a derived label.** IBM AMLworld labels
  *transactions*; we derive an *account* label ("participates in ≥1 laundering
  transaction"). A legitimate account merely receiving laundered funds becomes a
  positive. See *Labels* above; an edge-level metric on the native label is
  reported alongside.
- **The IBM AMLworld table below is populated only when the file is present.**
  At the time of writing the file had **not** been downloaded into
  `data/amlworld/`, so that table states so explicitly rather than being silently
  omitted or filled with a stand-in.
- Five seeds is enough to show variance, not enough for tight confidence
  intervals.
- `precision@k`/`recall@k` pool across test nodes; k is clamped to the pool size
  when the pool is smaller than k.
- AUC-PR saturates on the A1 product generator at its size (see *Why AUC
  saturates* in the generated block), which is why precision@k / recall@k are the
  headline metrics there. It does **not** saturate on the AMLSim-style data at
  its larger size.
- Betweenness centrality and the 3–8 hop cycle rule are computed **exactly**; the
  benchmark keeps its datasets at a size where they finish. No approximation is
  silently substituted (see the size-ceiling note in `amlsim_data.py`).
